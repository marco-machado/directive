# CLAUDE.md

This file provides guidance when working with code in this repository.

## Attribution

- Never add AI attribution footers to commits, PRs, or comments.

## Starting new work

Start every task from the latest `origin/main`, so the work never conflicts with or duplicates what has already landed.

- In the main checkout: `git switch main && git pull`.
- In a worktree (where `main` is checked out elsewhere): `git fetch origin main`, then `git merge --ff-only origin/main` if the branch has no commits of its own yet, or `git merge origin/main` if it does.
- Before opening a PR, fetch again and merge `origin/main` if it moved.

A `SessionStart` hook in `.claude/settings.json` fetches `origin/main` and warns when the branch is behind it.

## Commands

Node.js 24+. Install with `npm ci` (its `postinstall` reapplies `patches/@react-three+fiber+9.8.2.patch`; regenerate or drop it when upgrading R3F).

- `npm run dev`: Vite dev server on 0.0.0.0. The Cloudflare Vite plugin runs the Worker and the `PlayerCampaign` Durable Object locally in workerd, so `/api/*` works in dev. `.claude/launch.json` starts it on port 5173 (`--strictPort`). The dev save (the local Worker's storage and the browser's `ndPlayer`) is disposable: when checking a change, deploy missions, spend credits or start a new save freely; there is no need to protect it.
- `npm test`: Node's built-in runner with Node's type stripping over `tests/*.test.ts` (no Vitest/Jest).
- One file: `node --test tests/game.test.ts`
- One test: add `--test-name-pattern="<regex>"` to the command above.
- `npm run test:release`: the release check, local only. Builds, then Playwright (`tests/release/`) drives `vite preview` and the dev server in headless Chromium on the real GPU with real input (the smoke on both renderer backends: projects `smoke` and `smoke-webgl`), and fails on any console, page or network error, a failing step, or clipped text and off-screen controls. Needs `npx playwright install chromium` once. Do not add test hooks to game code for it.
- `npm run typecheck`: checks the browser code (`tsconfig.json`) and the Worker (`worker/tsconfig.json`) separately.
- `npm run build`: bundles `dist/`. The `three` chunk exceeds Vite's 500 kB warning; that is expected.
- `npm run cf-typegen`: run after editing `wrangler.jsonc` to regenerate `worker/worker-configuration.d.ts`.
- CI (`.github/workflows/verify-game-and-worker.yml`) runs test, typecheck, build, then `npx wrangler deploy --dry-run --outdir .wrangler/dry`. Every push to `main` deploys to Cloudflare after those checks.

Imports use explicit `.ts` extensions (`allowImportingTsExtensions`, `verbatimModuleSyntax`), which the Node test runner needs; use `import type` for types.

## Architecture

A React Three Fiber real-time squad tactics game served by one Cloudflare Worker. Its design pillar is engagement control, not stealth or combat; the README's Design section defines the terms (genre, pillar, core system, engagement, player fantasy), so use them as written. The README also has the full game rules and the API route table; keep it in sync when behavior changes.

**Simulation is the single source of game state.** `src/game/simulation.ts` holds a `Simulation` class that is plain TypeScript with no React or Three.js dependency, so the tests drive it directly (`sim.update(1/60)` in a loop; see the `arena()` helper in `tests/arena.ts` for an open, building-free map; the simulation's tests are split by topic into `game`, `alarm`, `movement`, `takedowns`, `progression` and `contracts`). One shared instance lives in `src/app.ts`. React DOM reads it through `useSyncExternalStore(sim.subscribe, sim.getSnapshot)`; snapshots are emitted at about 10 Hz, not every frame. The R3F scene advances it with `useFrame((_, dt) => sim.update(dt), -1)` in `src/scene/GameCanvas.tsx` and mutates Three.js objects per frame from `sim` directly rather than through React state. The class holds all mission state and keeps orders, combat and the update loop; the rest of its rules are functions over it in the same folder: `alarm.ts` (alarms, escalation, reinforcements), `hostiles.ts` (hostile behavior and fog of war) and `missions.ts` (objectives, followers, results, badges). Members those modules reach are public on the class; nothing outside `src/game` writes them. Tunable rules are exported constants in `src/game/rules.ts` (re-exported by `simulation.ts`), exported when another file uses them, and tests import them instead of hard-coding numbers.

**A contract type is one entry in each of four tables**, and the compiler asks for all four (`Record<ContractType, …>`): `CONTRACT_RULES` in `campaign.ts` (unlock tier, par, modifiers, badges, reward), `LAYOUTS` in `mapgen.ts` (what it places in the district), `MISSIONS` in `missions.ts` (objectives, target behavior, results, wording) and `CONTRACTS` in `src/ui/common.tsx` (title and briefing text). Add a rule to a table before adding a `type ===` check.

**Campaign rules are shared by browser and Worker.** `src/game/campaign.ts` contains pure functions (`startMission`, `completeMission`, `applyPurchase`, `applyRecruit`, `applyDismiss`, `clampCampaign`, migration) that take an injected `Rng`. The Worker's `PlayerCampaign` Durable Object (`worker/player.ts`, one instance per save code, a single `ledger` storage key) wraps a `CampaignStore` (`worker/store.ts`), which routes every write through them, so the server stays authoritative for credits, offers, roster, and payout. The client simulates the mission itself and the server trusts its stealth report. The server pays a contract once per deploy and no sooner than `MIN_MISSION_MS` after it.

**Client/server sync.** `Simulation` reports campaign events through the `CampaignSync` interface; `CampaignClient` (`src/net/campaignClient.ts`) implements it, queues requests, and pushes server replies back via `sim.applyCampaign`. If the Worker is unreachable, the game keeps running with `saveUnavailable` set and resyncs every 5 s; once the server answers, its campaign replaces local progress. The save code lives in `localStorage['ndPlayer']` and is written before the create call so a retry hits the same player. A legacy `localStorage['ndSave']` is imported once on create, then removed. `CAMPAIGN_VERSION` in `src/game/campaign.ts` is current; the DO upgrades an older ledger on read with `upgradeLedger`, which keeps a mission in flight and its payout claim. Bump it whenever the campaign's shape changes, and clamp the new field in `clampCampaign` (it drops anything it does not list).

**Determinism.** `src/game/mapgen.ts` builds a district (blocks, cover, patrols, objectives, posted-guard look schedules) from a contract's seed using `mulberry32` from `src/game/rng.ts`. `src/game/lots.ts` decides what stands in each block's room (`pickBlock`, then `fillBlock`: a plaza, a single building, a twin with an alley, or a corner of two touching buildings; shares in `BLOCK_MIX`); the street lattice itself does not depend on that, but lots draw from the same stream as what is placed afterward, so cover, patrols and objectives differ with them. A twin's alley is centered on a whole meter, where the navigation grid has its points; a room too narrow for that holds one building instead, so the shares are how often a kind is picked, not what ends up built (at tier 3 only 4 of 20 rooms can hold a twin). `layout()` returns the alleys and cover placement keeps off them, out to the streets, so an alley is always a way through. Any change to `lots.ts` or to the draws in `layout()` changes every map: contract 01 (`FIRST_CONTRACT` in `campaign.ts`) is a hand-checked seed, so recheck its quiet-route and bot tests and pick a new seed with the user if they fail. Contract 01 is recognized by its patrol cap, not its seed, so saves dealt with an earlier seed still work. `src/game/world.ts` provides navigation and line of sight.

**Rendering.** One renderer, three's `WebGPURenderer` from `three/webgpu`, created by `src/scene/renderer.ts`: it probes `navigator.gpu.requestAdapter()` and falls back to the renderer's WebGL 2 backend (`forceWebGL`) when there is no adapter or the URL has `?renderer=webgl`. Every custom shader is TSL (`three/tsl`) on node materials; there is no GLSL, `onBeforeCompile` or `ShaderMaterial`. Modules the unit tests import keep to plain `three`. The district's look is dressing derived from the plan, never gameplay: `src/scene/district.ts` is pure and seeded from the contract, never from mapgen's stream. It only composes: it picks the order and hands each asset a stream of its own (`stream(seed, name, index)` from `src/game/rng.ts`: one name per asset, the building's index for per-building ones; the ring gets one each for its cars, shops and puddles), so a new random draw for one asset never moves another's; give a new asset a new name instead of sharing one. A `Building` in `world.ts` is only a box, and two may touch; the composer passes each building's open walls (`openFaces` in `generators/faces.ts`) to `structure`, so nothing is hung on a wall inside a joint, and `sidewalks` cuts around neighbors. Its name and accent color are dressing too (`buildingNames` and `structure` in `generators/building.ts`), never fields the layout draws. Two things are shared on purpose: a building's `Structure` (name, accent, massing and wall order, which everything on that building is placed against) and the district's `SignAtlas` (`generators/signage.ts`), which hands out the atlas's 16 blade strips and 8 name boards in building order: a blade sign past the last strip shows one already there, and a name board past the last cell is not built, so no board ever shows another building's name. It also ranks the lights into the fixed pool of practicals and re-exports what other files import, while each asset's look is one module in `src/scene/generators/` (`building`, `storefront`, `signage`, `rooftop`, `street`, `lamp`, `car`, `ring`; `kit.ts` holds `Part` and the `Kit` they all push into). A generator is a function of its inputs and the `Rng` it is handed, imports no `three`, and a new asset is a new module there, not more code in `district.ts`. Cars and lamps are models, not boxes: their generators push one `Placement` each (`district.cars`, `district.lamps`) plus `hulls`, a few boxes and cylinders per prop whose overall extent the model must stay inside; they are tested and never drawn. `src/scene/propGeometry.ts` builds the two models in plain `three` (sizes come from constants in `generators/car.ts` and `lamp.ts`), with a `color` and a `surface` (roughness, metalness, glow, tint) per vertex; `props.tsx` draws each model once per district as an instanced mesh with the `prop` material, which gives the placement's color to vertices whose tint is 1. `tests/district.test.ts` keeps ground props off walkable ground and cover and keeps building parts inside the box `view.ts` uses for fades and silhouettes (footprint + `PLINTH`, up to `buildingTop`). Instanced parts carry per-instance data (`instanceFade`, `instanceData`, `instanceSize`) for the TSL in `materials.ts`. Emissive surfaces are authored above 1 (`Part.glow`, the facade window gain) so the bloom pass's threshold picks them out; lit surfaces stay below it. Tone mapping is Neutral, and the renderer applies it to the whole frame at the end (materials' `toneMapped: false` has no effect), so HUD-colored overlays look the same with bloom on or off. `BLOOM.strength` is on `UnrealBloomPass`'s scale, which `bloom.tsx` triples for `BloomNode`.

**Camera.** `src/scene/framing.ts` (framing math) and `src/scene/drag.ts` (telling a drag from a click) are pure and unit-tested. The camera frames the `.view-frame` element, the area the HUD leaves free, not the full canvas.

**Worker routing.** `wrangler.jsonc` runs the Worker first only for `/api/*`; everything else is static assets with SPA fallback. `worker/index.ts` applies the rate limits and the body cap; `worker/routes.ts` (`handleApi`) maps routes onto the store's methods and turns `{ ok: false, status }` results into 400/404/409 responses. `routes.ts` and `store.ts` import nothing from Cloudflare so `tests/worker.test.ts` can drive them with a Map for storage; keep it that way. A save that never deployed expires 30 days after creation (the DO's `alarm`). `public/_headers` carries the Content Security Policy: a new outside source must be listed there.

`artifacts/game-progress.md` holds the `threejs-game-director` skill's working notes and the design decisions behind past passes; it is history, not a spec.
